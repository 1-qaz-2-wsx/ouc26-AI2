# PDB与BFS/BiBFS比较：报告章节初稿

本文件为组长模块的可编辑初稿，不是完整小组研究报告。理论和实现可整合到报告的启发函数、算法实现章节，实验摘要放性能分析章节。写作依据为当前代码和2026-10-26实测；难例性能尚未通过，不得删除该限制。

## 1. 不相交模式数据库

模式数据库将一部分搜索工作提前到预处理阶段。对于15数码，将数字划分为G1={1,2,3,4,5}、G2={6,7,8,9,10}、G3={11,12,13,14,15}。每个抽象状态记录空格和本组五个数字的位置，其余数字不可区分。数据库保存从抽象状态到抽象目标的最小分组代价。

移动本组数字时边权为1，移动其他数字时为0。由于存在零代价边，预处理使用反向0–1 BFS：零代价改进入队首，一代价改进入队尾，不使用普通BFS的首次访问即确定距离规则。数字组互不相交且完整覆盖数字，每个真实移动恰好由一个组收费。

令h_i(s)为第i组的抽象最短距离，实际某条解路径在第i组的累计收费为c_i。投影后仍是一条合法抽象路径，所以h_i(s)≤c_i。对全部组相加得到h(s)=Σh_i(s)≤Σc_i=真实路径长度，对最优路径同样成立，因此启发函数可采纳。

对任意真实一步s→s'，抽象最短路满足h_i(s)≤c_i(s,s')+h_i(s')。逐组相加且Σc_i(s,s')=1，得到h(s)≤1+h(s')，故具有一致性。该证明依赖正确的费用划分，不能将各组按全部移动收费后相加，也不能再直接加整盘曼哈顿。

这种不相交子目标的加性构造与Korf、Felner的工作一致，本文具体程序采用保留空格位置的0–1代价抽象。[Korf与Felner，2002，Disjoint pattern database heuristics](https://doi.org/10.1016/S0004-3702%2801%2900092-3)；相关加性抽象理论见[Yang等，A General Theory of Additive State Space Abstractions](https://arxiv.org/abs/1111.0067)。

## 2. 紧凑存储与可复用加载

空格及五个指定数字占六个不同位置，排列数量为P(16,6)=5,765,760。使用部分排列排名把每个有效位置元组映射到连续下标，而非分配16^6稀疏槽位。排名逐个扣除之前占用且小于当前位置的位置数，再用混合进制累积。建表队列携带压缩位置元组，距离表以byte保存；255为未访问标记。

三组距离数据共17,297,280字节，约16.5MiB；这是距离数组大小，不是整个Java进程内存。建表双端队列、对象、文件序列化与加载缓冲区还占额外空间。预处理从各组抽象目标出发，松弛所有0/1边；旧队列条目的距离已过期时跳过。

数据库缓存按棋盘规模、完整目标和完整分组选择，格式带版本、长度及CRC32。不同目标或不同分组不能混用。文件先写临时快照，再替换目标文件。首次调用loadOrBuild生成并保存；后续进程直接加载。已存在但损坏的文件抛异常，不自动当作无解或静默替换。

## 3. 搜索引擎接口

DisjointPatternDatabase.predictor()提供课程框架已有的Predictor。A*和IDA*都在初始化时取得同一对象，节点估值只在内存查表，不执行文件操作。适配器检查查询棋盘规模及目标匹配。组长负责PDB与接口，C负责IDA*搜索，B负责优先队列及A*比较；本轮未改core。

第一阶段3×3小模式原型继续保留，用于独立编码交叉验证。新实现对181,440个真实8数码状态检查可采纳性和一致性；对正式4×4检查1806个精确浅层状态和10000条随机边。4×4短例由已知4步路径和曼哈顿下界共同确定最优长度，两搜索器均返回合法4步路径。不能由有限测试推断已经穷举验证全部15数码状态。

## 4. BFS与BiBFS的适用范围

在单位代价、可逆、目标已知的单对起终点问题中，BFS从起点逐层扩展；BiBFS同时维护起点和目标两侧的已访问距离，每次扩展较小前沿的完整一层并检查相遇。理想树状模型中，搜索深度从d分摊到两侧约d/2，可能减少大量扩展；实际效果受重复状态、边界宽度和目标分布影响，并非所有问题都固定获得某一倍数加速。

本次31步8数码题，BFS展开181438个状态，BiBFS展开12452个状态；3次测量wall中位数分别313.092ms、23.015ms。小两步题的计时非常短，不据此比较微小性能差。访问条目和前沿数是结构计数，不是实际内存占用。

普通BFS/BiBFS不能直接用于本实现的PDB加权图。PDB要得到“所有抽象状态到目标”的距离表，而非一个起点到目标的答案；且边权为0或1。单对双向搜索即使找到最短路径，也没有顺带完成整张数据库。因此正式建表使用反向0–1 BFS，而BFS/BiBFS比较用于相同的单位代价真实棋盘求解任务。不能把此比较写成“BiBFS使PDB建表加速”。

## 5. 性能结果与局限

Windows11、AMD Ryzen7 8745H、Java25.0.4.1、最大堆768MiB下，默认数据库一次构建并保存3091.940ms，显式重载180.956ms；均为单次数据，不能替代多轮稳定性能分析。

指定困难实例为15..4、3、1、2、0的逆序棋盘，标准目标。曼哈顿44，PDB52，表明该例的初始下界更强，但更强下界不等于一定在规定时间内解出。C第一阶段IDA*联合实测在约60秒后超时，展开约7469万个节点，未返回解；不能报告最优解长或宣称一分钟目标达成。具体实验数据及后续复测见experiments/PDB第二阶段实测.md，最终报告以最新复测为准。

CPU时间通过JDK ThreadMXBean记录当前搜索线程消耗，不是整个进程CPU总量。若环境不支持则写N/A；极短任务出现0源于时间分辨率，不代表零计算量。报告应分别列预处理、加载和搜索时间，透明说明一分钟口径。

后续由组长与C共同评估更强分组/对称估值、路径去环、后继排序和减少节点分配等方向；本稿不声称这些尚未实现的优化已带来收益。公共Feeder统一入口、B队列最终整合和可视化联调也不能由本模块测试替代。
