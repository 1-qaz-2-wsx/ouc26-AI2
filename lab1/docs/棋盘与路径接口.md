# 棋盘与路径接口约定 v1

此文件是组长提出的共同实现约定，不表示现有骨架已经提供这些方法。A 实现棋盘与问题接口，B、C 和组长按约定调用。接口变更先在合并请求中说明影响。

## 通用规则

- 棋盘边长为 3 或 4，一维行优先排列，位置从 0 开始，空格数字为 0。
- 目标棋盘由输入提供，不写死为标准目标；每步代价为 1。
- 棋盘不可变；构造时复制数组，返回数组也复制。一次移动产生新棋盘，不改父状态。
- 数字必须恰好包含 `0..size*size-1`，无重复；非法输入抛 `IllegalArgumentException`。
- `equals` 比较边长和所有数字，`hashCode` 必须与其一致；哈希相同不能直接认为棋盘相同。
- 方向指空格移动，`UP/DOWN/LEFT/RIGHT`；行向下增长、列向右增长。

## A 提供的棋盘接口

包：`stud.g01.problem.npuzzle`。

```java
public PuzzleBoard(int size, int[] tiles);
public int size();
public int tileAt(int index);
public int blankIndex();
public int[] toArray();
public boolean canMove(Direction direction);
public PuzzleBoard move(Direction direction);
public int misplaced(PuzzleBoard goal);
public int manhattan(PuzzleBoard goal);
```

以上为方法签名清单，不是可直接编译的类。`Direction` 为同包新增枚举；`PuzzleMove extends Action` 提供 `PuzzleMove(Direction)`、`direction()`、`stepCost()`（恒为 1）和 `draw()`。

`tileAt` 越界抛 `IndexOutOfBoundsException`，不合法的移动抛 `IllegalArgumentException`；目标边长不同抛 `IllegalArgumentException`。错位和曼哈顿均不计空格，使用传入目标的位置。

继承 `State` 的 `draw()` 显示文本棋盘，空格显示 `#`。`actions()` 按 UP、DOWN、LEFT、RIGHT 返回四个候选动作；`NPuzzleProblem.applicable` 负责过滤，`next(Action)` 返回相应新棋盘。这样与课程 `Problem.childNodes` 的流程一致。

## 问题、启发函数及队列

A 的 `NPuzzleProblem` 保留已有构造器，两个参数的构造器从棋盘取得边长。提供 `initialBoard()` 和 `goalBoard()`，返回不可变棋盘。`solvable()`比较初始与目标的可达性类别，`stepCost` 返回 1，`goal` 使用棋盘相等判断。

A 提供同包 `PuzzleHeuristics`：`public static Predictor predictor(HeuristicType type)`。第一阶段支持 MISPLACED 和 MANHATTAN；尚未实现的类型明确抛 `UnsupportedOperationException`，不能返回 null。组长后续提供PDB，A统一接入，避免不同成员同时改Feeder。

A 的 `PuzzleFeeder.getProblems` 使用课程每行格式：边长、初始的 size*size 个数字、目标的 size*size 个数字；允许任意空白分隔，忽略空行，非法输入指出行号。Feeder 保留无参构造器供反射创建。

B 的 `PqFrontier` 提供 `PqFrontier(Comparator<Node> comparator)`，供Feeder使用 `Node.evaluator(type)`；遵守 Frontier 的重复状态约定。清空时同时清理辅助索引；不要因堆中残留旧条目造成错误取出或错误 isEmpty。辅助哈希索引以 State 为键，不使用缺少对应 hashCode 的 Node。

C 后续提供 `IdAStar(Frontier frontier, Predictor predictor)`，保留原单参数构造器时明确默认策略。原框架调用的是另一个包下的类，具体兼容接入由组长集中处理，见编译问题记录。

## 解路径文件 v1

A 负责导出，D 负责读取。一个文件对应一个问题，播放器通过目录或文件列表加载多个问题。UTF-8纯文本，无需 JSON 库。格式：

```text
NP_PATH_V1
size 3
status SOLVED
moves 1
states 2
goal 1 2 3 4 5 6 7 8 0
state 0 1 2 3 4 5 6 7 0 8
state 1 1 2 3 4 5 6 7 8 0
```

- `state` 后第一个整数是步号，其后为所有棋盘数字；第0步为初始状态。
- SOLVED：`states = moves + 1`，最后一帧必须等于 goal，每两帧只交换空格及相邻数字。
- 初始即目标：moves 0、states 1，不应当作无解。
- UNSOLVABLE：moves -1、states 1，只保存初始状态及目标；播放器显示无解，不播放。
- 超时或异常不能记为 UNSOLVABLE；第一阶段失败时不导出伪造路径，结果表记录 TIMEOUT/ERROR。
- `generatePath` 返回的队列不含根节点，A 导出时必须单独加入初始状态。

A 新增 `SolutionPathWriter.write(Path output, NPuzzleProblem problem, Deque<Node> path)`，明确抛 IOException；目录由导出器创建。path=null 只有在已经确认不可解时才能导出 UNSOLVABLE，否则记失败。`showSolution` 可打印文本，新增加的测试入口负责指定导出文件名，原框架不用为路径导出随意改动。

`examples/paths` 的两个文件由人工构造，只供文件格式、路径合法性及界面测试，不属于求解器实验数据。

## 第一阶段最低交叉检查

- 标准目标的两种启发值均为 0；一移动状态均为 1。
- 修改构造时传入的数组不能改变棋盘；相等棋盘的 hashCode 必须相同。
- 角、边、中心空格分别产生 2、3、4 个合法后继。
- 标准目标中交换两个数字后判断不可解；非标准目标也做可解性判断测试。
- B/C 在一移动、两移动样例上返回正确路径；难例最优性需独立基准验证，不能只凭两种算法相同就宣称最优。
